# V3 — Software Requirements Specification

Status: scoped, not implemented. Entry gate: both the [V2 cleanup, C09](v2-cleanup.md#slice-c09--cleanup-completion-gate) gate and the [V2 cleanup follow-up gate](v2-cleanup-followups-gate.md) (F05) must be closed before any milestone starts. Cleanup owns A1–A8; these milestones extend the corrected behavior and must preserve its regression guarantees.

Product scope: a local CLI for developers turning bounded tasks in existing Git repositories into isolated patches with independent review, inspectable evidence, and operator-controlled execution. Deliver milestones 1–5 in order, with slices in their listed order. New command names below are required interfaces, not claims of current availability.

Initial release scope is Linux with the existing declared Python minimum. Hosted dashboards, native Windows support, custom filesystem/search tools, new providers, autonomous merging, and a plugin marketplace are excluded. Existing console-script and module invocation forms remain supported.

Companion: [executive summary and requirement report](srs-review.md). Requirements here are normative; that report summarizes them. The trust model is one local operator using trusted repositories and explicitly configured commands. Agent text and imported bundles are not controller authority. Hostile-repository containment, multi-user access control, and a new OS sandbox are excluded.

## Milestone 1 — Execution foundation

### Slice V00 — Command, lifecycle, and resource contracts

**Problem description / scope.** Stage completion, command success, and accepted changes are different outcomes. Unbounded output and private runtime data also need explicit operating limits. Scope: shared CLI, lifecycle, and non-functional contracts for all later slices.

**Functional requirements**

- V00-FR1: Persist run lifecycle separately from stage progress, review decision, and evidence freshness. Each background launch shall return a durable run ID; status and tail shall use that run's terminal record, not the existence of an older report, including when preflight fails.
- V00-FR2: Document and preserve the existing exit-code categories. Foreground `run` success shall require current acceptance; `verify` success shall require all required checks to pass. Successful status/report/export means the requested operation succeeded, not that the task was accepted; background success means launch only. Snapshot JSON modes shall emit one versioned result on stdout and diagnostics on stderr; V16's later explicit JSON Lines mode shall emit one versioned event per line.
- V00-FR3: Status and reports shall remain usable during execution without provider calls, acquiring execution ownership, or changing execution state. They shall expose incomplete records as pending/unknown rather than guessing success.

**Non-functional requirements**

- V00-NFR1: Capture subprocess output incrementally with bounded in-memory buffers. Initial configurable limits shall be 64 MiB combined stdout/stderr per invocation and 1 MiB per parsed event. Overflow shall cause managed cancellation and an explicit incomplete result, never silent truncation presented as success. Limits shall apply to agents, checks, and setup commands.
- V00-NFR2: New private runtime directories/files shall use owner-only permissions. Structured metadata shall exclude credential values; raw local outputs may contain sensitive data and shall be documented as private. Optional reasoning capture shall default off for new configurations while preserving explicit existing choices. Retention shall be manual; no automatic evidence deletion is introduced.

**Constraints.** Preserve existing invocation forms and exit categories: success 0, validation/rejection 1, bad input 2, blocked 3, locked 4, interrupted 130. A stable reason field shall distinguish failures within those categories. Resource limits are proposed initial defaults, not measured optimal values. Do not promise that local transcripts or exported source are secret-free.

**Acceptance.** Repeated background runs cannot reuse another run's completion; foreground rejection and successful report retrieval are distinguishable. A noisy fixture is stopped at its configured limit without unbounded buffering; filesystem permission and credential-metadata tests pass.

### Slice V01 — Explicit project context and validated records

**Problem description / scope.** Runtime paths depend on import-time cwd, and malformed configuration/state can crash outside the supported error paths. Scope: project resolution, configuration validation, and durable record compatibility.

**Functional requirements**

- V01-FR1: Commands shall resolve the containing Git worktree from any subdirectory and accept an explicit `--project PATH`. A run shall use one resolved context for its project, task, workspace, effective configuration, and evidence paths.
- V01-FR2: Configuration and persisted records shall validate supported schema versions, root/nested types, role references, command arguments, and numeric limits before use. Invalid input shall produce an actionable nonzero CLI outcome before provider dispatch.
- V01-FR3: Existing valid configuration shall remain loadable. Unsupported/damaged records shall remain available for diagnosis; migration shall not grant acceptance to legacy evidence lacking cleanup-required provenance.
- V01-FR4: Schema migrations shall be versioned, performed under task/configuration ownership, and recoverable with the previous record retained. An older binary shall refuse to mutate a newer unsupported schema; an interrupted migration shall not leave mixed authoritative versions.
- V01-FR5: Validate task identifiers and resolve paths against their designated roots, rejecting traversal and symlink escapes for controller-managed reads/writes. Publish the tested Git feature matrix; unsupported repository states or features shall block affected operations before dispatch/export rather than produce partial source identities or patches.

**Constraints.** Reuse cleanup's execution guards and durable records. Do not redesign stage ordering or storage technology. Root discovery shall not initialize a second task/config tree in a subdirectory.

**Input from the V2 cleanup follow-up audit.** Audit I11 (2026-09-25), deferred here by operator decision: per-path source-identity fingerprints recorded in `state.json` grow without bound as evidence accumulates. V01's record validation and schema-migration work shall bound or relocate them without weakening source-identity strictness or the durable evidence the cleanup gates rely on.

**Acceptance.** Root, subdirectory, and explicit-project invocations resolve the same task. Malformed records, interrupted migrations, traversal, and unsupported Git states produce controlled errors without agent calls or data loss. Ordinary repositories and linked worktrees, including binary files, modes, and symlinks, are covered; unmerged indexes and unsupported submodule, sparse-checkout, or LFS cases fail explicitly.

### Slice V02 — Installable, continuously checked release

**Problem description / scope.** Installation verification is opt-in, assumes the old distribution name, and lacks a tracked release gate. Scope: package build/install checks and supported-runtime documentation.

**Functional requirements**

- V02-FR1: CI shall install declared build prerequisites, build the `catenna` distribution, install its wheel into a fresh environment, and exercise both invocation forms from outside the checkout.
- V02-FR2: CI shall run unittest, `mock-test`, and cleanup regressions on Linux using the declared minimum Python and the project's selected development Python. Installed mock fixtures/tests required by supported commands shall be included.
- V02-FR3: Release documentation shall state supported runtimes, installation steps, and the required checks. Generated build/metadata directories shall be ignored without deleting existing artifacts.
- V02-FR4: Each milestone gate shall map its requirement IDs to executable checks or explicit inspection/evaluation evidence, recording revision and environment. Skipped required checks and unsupported advertised capabilities shall prevent release of that milestone.

**Constraints.** Release checks require no provider credentials or model calls. Do not expand platform support or include private task/transcript data in distributions.

**Acceptance.** A clean build/install passes the CLI and mock smoke checks; missing runtime package data and the obsolete wheel-name assumption are caught automatically. V00–V02 passing closes milestone 1.

## Milestone 2 — Complete local developer workflow

### Slice V03 — Initialization and preflight

**Problem description / scope.** New users must discover prerequisites and protect local task data manually. Scope: `init`, new `doctor`, and provider-free first-run guidance.

**Functional requirements**

- V03-FR1: `init` shall initialize the resolved project idempotently, preserve existing configuration unless explicitly replaced, and establish an ignore rule for private task/transcript data without overwriting user ignore rules.
- V03-FR2: `doctor` shall report configuration validity, Git/workspace readiness, configured CLI availability/version, configured verification commands, and whether the role configuration permits independent required reviewers. Checks shall report pass, fail, or unknown with a corrective action.
- V03-FR3: A documented example shall take a user from installation through a local fake-agent task and its final report without credentials or manually creating internal state files.
- V03-FR4: `run` shall enforce applicable preflight checks before paid dispatch and repeat affected checks when configuration/workspace inputs change. Required final review shall use a different configured provider agent from implementation; unavailable independent review shall block, even before V09 adds the full capability matrix.

**Constraints.** Preflight shall not start a model session, install software, or change authentication. Binary presence shall not be presented as proof of account access. Command discovery shall not execute project scripts.

**Acceptance.** Fresh initialization is repeatable, private runtime files are ignored, missing prerequisites are explained, and the documented demo completes from a clean directory.

### Slice V04 — Task creation and acceptance contracts

**Problem description / scope.** Task seeding requires undocumented manual construction, while free-form requirements do not map directly to evidence. Scope: new `task new NAME --request FILE` and pre-run task validation.

**Functional requirements**

- V04-FR1: Task creation shall preserve the supplied request and generate Stage 0/1 documents plus a versioned structured contract containing objective, included/excluded scope, repository-relative context paths, and acceptance criteria with unique IDs.
- V04-FR2: Each criterion shall reference configured executable checks, an explicit manual checkpoint, or both. Unfilled fields, nonexistent check references, and invalid context paths shall block dispatch with actionable validation errors.
- V04-FR3: Contract changes shall participate in existing artifact/evidence invalidation. Existing task documents shall remain accessible, with missing contract fields identified rather than inferred as satisfied.
- V04-FR4: The versioned `task.json` contract shall be authoritative for scope and criteria; Stage 0 shall preserve the original request and Stage 1 shall be its readable contract projection. Divergence between contract and projection shall block dispatch until explicitly reconciled through documented editing/validation. Criterion IDs and contract revisions shall remain traceable; neither representation shall silently override the other.
- V04-FR5: The contract shall define allowed change paths/patterns and explicit exclusions. Changes outside that boundary shall block acceptance until the operator explicitly amends the contract and affected evidence is renewed; unexpected files shall not be silently deleted or treated as in scope.

**Constraints.** Creation shall not spend tokens, invent task requirements, or overwrite an existing task. Generated placeholders are editable drafts, not runnable requirements. No new requirements-generation agent is included.

**Acceptance.** Creating a task produces a bounded editable draft; completing its required fields makes it runnable. Every criterion has an explicit evidence source and remains traceable in later results.

### Slice V05 — Dedicated task worktrees

**Problem description / scope.** Cleanup safely serializes a shared worktree; developers still need task isolation from their active checkout. Scope: new-task workspace creation and routing.

**Functional requirements**

- V05-FR1: Before a new task's first agent invocation, Catenna shall create or reuse its dedicated Git worktree from a recorded execution-base commit, with a unique task branch/path. Record workspace identity and delivery-base commit durably. These bases coincide for a new task; V07 defines follow-up inheritance.
- V05-FR2: Planning, implementation, checks, review, and source fingerprints shall all resolve against that worktree. Task/control records shall remain associated with it regardless of the caller's directory.
- V05-FR3: Dirty changes in the caller's checkout shall not be copied, stashed, reset, or treated as task input. Unsupported workspace setup shall stop with a reason before agent dispatch. Existing shared-worktree tasks shall remain pinned to their original workspace under cleanup's exclusive ownership rules.
- V05-FR4: Support explicitly configured workspace-preparation argv commands with timeouts; record their outcomes, configuration, relevant dependency-file hashes, and declared runtime versions. Failed preparation shall block dispatch, and tracked/non-ignored source changes shall require explicit reconciliation. Do not silently install dependencies or copy ignored environments/secrets from the developer checkout; reuse preparation only while its recorded inputs remain current.
- V05-FR5: Keep authoritative controller records outside the agent-writable task worktree, exposing only needed task inputs and designated candidate outputs. Persist workspace creation intent so interrupted setup can resume without adopting an unrelated directory or branch.
- V05-FR6: Required review shall receive an immutable patch/source snapshot of all changes from the delivery base, including committed and untracked changes, bound to the same identity used by verification and export. A clean Git status shall not imply an empty task change; review shall not depend only on a dirty-file manifest.

**Constraints.** Require an existing base commit. The execution base is the task's starting source; the delivery base is the integration revision against which its complete patch is exported. Preserve worktrees and branches after completion/cancellation; automated deletion and migration of in-flight tasks are excluded. Preparation is a recorded local setup step, not a container/environment manager; concurrent worktrees do not isolate external databases/services.

**Acceptance.** Two new tasks operate on different source trees while the developer's dirty checkout remains unchanged; resume returns to the recorded workspace and base.

### Slice V06 — Project verification and manual evidence

**Problem description / scope.** Generic command execution exists, but project setup, useful failure details, and criterion coverage are incomplete. Scope: verification configuration, results, and new `record-test TASK --criterion ID --decision VALUE --notes FILE`.

**Functional requirements**

- V06-FR1: Provide editable pytest and npm-test configuration examples using the existing argv runner. Explicit project commands shall determine routine verification; Catenna self-tests and implicit Java/Gradle checks shall not be prerequisites for unrelated projects.
- V06-FR2: Each check shall record its ID, argv, cwd, source identity, start/end, exit/timeout/launch outcome, and raw output paths. Known runner formats shall additionally expose test names and file/line messages when available; unknown formats shall retain the generic result.
- V06-FR3: Manual evidence shall record the criterion, decision (`accept`, `reject`, or `needs_followup`), notes, time, and current source identity; only `accept` satisfies the criterion. Task acceptance through either the automatic or manual Stage 6 route shall require all mapped executable checks to pass and all required manual criteria to have explicit passing evidence; a manual Stage 6 decision shall not waive failed or missing criterion evidence.
- V06-FR4: Criterion results shall distinguish passed, failed, and unverified. A passing unrelated command or heuristic coverage signal shall not satisfy an unmapped criterion; source drift shall invalidate its evidence.
- V06-FR5: Bind results to contract revision, check configuration, workspace preparation, and declared runtime identities as well as source. Known test formats reporting zero tests, all tests skipped, or malformed required result data shall remain unverified even with exit zero. Unknown formats may establish configured command success, not inferred test coverage. Later failing/incomplete attempts shall supersede earlier passes under C06.

**Constraints.** Do not add a testing framework or execute discovered commands without configuration. Preserve the user's environment/toolchain and raw output. Do not infer behavioral coverage from textual symbol references.

**Acceptance.** Example Python/JavaScript tasks expose usable check results; an unmapped, failed, or missing manual criterion prevents acceptance, and corrected evidence allows continuation.

### Slice V07 — Supported cancellation and follow-up

**Problem description / scope.** Users need commands to act on blocked/rejected work without editing controller state. Scope: new `cancel TASK`, `followup TASK --name NAME`, and existing retry approval/resume interfaces.

**Functional requirements**

- V07-FR1: `cancel` shall target only the task's recorded active run, invoke cleanup's ownership/process termination behavior, and report stopped, already inactive, or blocked/uncertain. It shall preserve changed files and evidence.
- V07-FR2: Status shall expose the active run, terminal outcome or blocking reason, pending approval, and the supported next action. Approval/resume shall consume existing bounded retry authorization; neither shall reset attempt history implicitly.
- V07-FR3: `followup` shall create a draft task referencing the parent's rejected/needs-followup findings, affected criteria, and evidence. It shall not alter the parent's decision or start implementation automatically.
- V07-FR4: A follow-up shall start from an immutable checkpoint of the exact parent source under review, captured under workspace ownership, and retain the parent's original delivery base. If that source is unavailable or has drifted, creation shall block rather than substitute current HEAD. Inherit applicable parent criteria plus the correction criteria; the child shall earn its own verification/review evidence. A controller-owned checkpoint shall not commit or alter the developer checkout.

**Constraints.** No indefinite repair loop, automatic approval, or arbitrary PID cancellation. Follow-up creation shall fail rather than overwrite an existing task and shall require V04 validation before running.

**Acceptance.** A user can cancel an active background run, approve one pending retry, and create a bounded correction task using documented commands without editing state JSON.

### Slice V08 — Reports and exportable changes

**Problem description / scope.** Developers need a reviewable change and its evidence outside Catenna's internal files. Scope: `report TASK --json` and new `export TASK --format patch|bundle --output PATH`.

**Functional requirements**

- V08-FR1: Human and versioned JSON reports shall expose run/task/workspace identity, execution/delivery bases, current source identity, current versus historical decision, criterion/check results, unresolved findings, effective agents/models, usage completeness, and next action. JSON stdout shall contain only the JSON result. Fields not yet observable before V09/V10 shall be explicitly unknown, not guessed or omitted as if complete.
- V08-FR2: Patch export shall describe all task changes relative to the delivery base, including committed, staged, unstaged, deleted, renamed, and non-ignored untracked content; follow-up export shall include inherited parent changes. Bundle export shall add both bases, resulting Git tree identity, patch identity, and structured review/verification evidence; equivalent source content shall remain identifiable after the patch is committed elsewhere.
- V08-FR3: Export shall take a consistent source snapshot and label incomplete/stale/rejected results accurately. Bundle metadata shall use an explicit field allowlist, excluding raw prompts, transcripts, reasoning traces, environment values, credential fields, and host-absolute paths by default.
- V08-FR4: Publish export outputs atomically only after their contents and manifest digests are complete. Concurrent source mutation, cancellation, storage failure, or an existing/symlink output target shall not leave an apparently completed export or overwrite other files.

**Constraints.** Do not apply, commit, push, or merge during export; do not overwrite an existing output. Exported source and narrative findings are not guaranteed secret-free. Existing report consumers need explicit schema-version compatibility.

**Acceptance.** An exported accepted patch applies to a clean checkout of its delivery base, including for a follow-up; its report refers to the same evidence. A developer completes an example task through export without editing internal state. Failed export cannot masquerade as a completed bundle. V03–V08 passing closes milestone 2.

## Milestone 3 — Measured efficiency and integration

### Slice V09 — Capability-aware provider settings

**Problem description / scope.** Some settings have no effect, and a stage model override can be forwarded to an incompatible fallback provider. Scope: existing provider adapters and routing configuration.

**Functional requirements**

- V09-FR1: Each adapter shall declare supported model, effort, budget, structured-output, and execution-mode controls. Explicit unsupported settings shall fail preflight instead of being silently ignored.
- V09-FR2: Role overrides shall be provider-specific; fallback shall use its own valid settings. Dispatch records and reports shall distinguish requested from effective settings and identify the adapter/CLI version.
- V09-FR3: Supported controls shall reach the subprocess invocation through documented provider interfaces, covered by adapter fixtures. V3 profiles shall enforce strict reviewer independence: the final reviewer must use a different configured provider agent from the implementer. Missing eligible reviewers or incompatible degraded-review settings shall block at preflight.
- V09-FR4: Publish tested CLI versions and event-schema fixtures for each adapter. Unrecognized required completion/error data shall produce an unsupported/unknown outcome, not guessed success. Provider-specific extra arguments shall not weaken execution permissions, bypass the configured limits, or replace controller-owned output routing.

**Constraints.** No new providers, guessed flags, or automatic model selection policy. Legacy ambiguous overrides shall require a clear correction before affected dispatch.

**Acceptance.** Changing a supported setting changes the captured invocation; unsupported settings block before spending; fallback never inherits another provider's model identifier.

### Slice V10 — Task budgets and complete usage reporting

**Problem description / scope.** Per-stage retries do not bound total task work, and partial usage can appear complete. Scope: aggregate budgets, existing ledger data, and task reports.

**Functional requirements**

- V10-FR1: Add task-wide maximum agent calls and execution duration, counting retries, fallbacks, and overseer calls across resume. Duration shall count controller execution time, including child/check waits, but exclude time awaiting human action. Limits shall be persisted; an exhausted limit shall prevent another dispatch, and an elapsed active limit shall use managed cancellation.
- V10-FR2: Provider token/cost limits shall be advertised as hard limits only when the adapter can enforce them during execution. Otherwise, report them as estimates or between-call thresholds, including missing observations and possible overshoot.
- V10-FR3: Reports shall show configured budgets, consumption, and remaining allowance; separate observed input/output/cache tokens, provider-reported cost, estimated cost, and unknown data; and identify missing runs while aggregating by task/stage/provider/effective model. Cache accounting shall be normalized with provider-specific fixtures before aggregation.
- V10-FR4: Require finite positive call/duration limits before execution, with editable values in supplied task/profile templates. Reserve call allowance durably before dispatch under task ownership; uncertain launches shall remain consumed, and crashes/resume shall not replenish counters. Persist timed intervals so unconfirmed execution time is reported and conservatively charged until reconciled.
- V10-FR5: Provide `budget TASK --max-calls N --max-seconds N --reason TEXT` for explicit amendments while execution is inactive and ownership is held. Record previous/new limits and reason, preserve consumption, and reject limits below consumption. Increasing allowance shall not approve a retry or start work automatically.

**Constraints.** Resume and retry approval shall not replenish budgets. An explicit budget amendment shall preserve previous usage and record the amendment. No promise of exact subscription billing or hard enforcement from a completion-only ledger.

**Acceptance.** Retries/resumes cannot exceed call limits through counter reset; duration exhaustion cancels safely. Missing usage remains visibly unknown instead of zero or a falsely complete total.

### Slice V11 — Workflow profiles and comparative evaluation

**Problem description / scope.** The default seven-call workflow has no measured efficiency advantage for every task. Scope: one explicit simpler profile and a bounded comparison against the existing thorough profile.

**Functional requirements**

- V11-FR1: Preserve the existing workflow as `thorough`. Add an opt-in `compact` profile using the validated task contract, one implementation-brief stage, implementation, project verification/manual evidence, independent diff review, and deterministic final decision; omit specification/audit, separate brief-gate, and overseer calls in this profile.
- V11-FR2: Profile choice and applicable stages shall be recorded before execution. Omitted stages shall be explicitly not applicable, never fabricated as passed. Profiles shall preserve cleanup guarantees, task acceptance criteria, budgets, and independent final review.
- V11-FR3: Evaluate both profiles on the same versioned set of at least twelve tasks across Python and JavaScript fixtures, including bug fixes, refactors, failing checks, and interrupted runs. Publish raw outcomes, independently checked correctness, human review time, execution time, usage completeness, and estimated/reported cost separately.
- V11-FR4: Use a versioned profile stage graph to define required transitions and evidence inputs. In `compact`, bind the validated contract and implementation brief in place of the omitted brief-gate artifact; controller-owned verification/handoff rules still apply. Resume shall use the recorded graph version and shall never fabricate absent artifacts to satisfy thorough-profile checks.
- V11-FR5: Fix task bases, acceptance rubrics, provider/model settings, and budgets before comparison; disclose any differences between profiles. Include failed, rejected, cancelled, and incomplete attempts in the published totals and retain unknown usage. Report the measured sample and its limitations; do not generalize twelve-task results into a universal savings or quality guarantee.

**Constraints.** `compact` shall not become the default merely because it is cheaper or completes more stages. Profile changes on an in-flight task are excluded. Live evaluation is an explicitly invoked activity with configured budgets, not a routine CI requirement.

**Acceptance.** Both profiles preserve acceptance/recovery invariants. A recorded comparison using configured live providers identifies quality and efficiency tradeoffs; fixture-only results or completion counts alone do not establish model quality or savings.

### Slice V12 — CI evidence consumption

**Problem description / scope.** Teams need to consume Catenna results without parsing prose or granting publishing authority. Scope: documented CI use of existing exit outcomes, JSON reports, and exported bundles.

**Functional requirements**

- V12-FR1: Provide one CI example that consumes a completed task's JSON/bundle and fails its gate for stale, incomplete, rejected, or unverified required evidence. Background-launch success shall not be interpreted as task success.
- V12-FR2: CI artifacts shall include the patch/base/resulting-tree identities, criterion/check outcomes, review decision, and schema version. The gate shall compare the recorded base and resulting source tree with the revision under review, independent of whether the original patch was committed at verification time; a mismatch shall fail the gate.
- V12-FR3: Document credentials and trust boundaries separately for any optional live agent run; local fixture-based evidence consumption shall work without provider credentials.
- V12-FR4: The CI gate shall establish evidence origin from an explicitly trusted producer/job and bind it to the expected repository, run, and verification-policy revision. Digest consistency alone shall not authenticate evidence. Contributor-controlled bundles/reports shall not authorize the gate without trusted reproduction or attestation from that producer.

**Constraints.** Automatic PR creation, remote publishing, hosted execution services, and merging are outside this V3 scope. Reuse V08's report/export formats rather than adding a second evidence protocol. Local exports are inspectable evidence, not self-authenticating attestations; use the CI platform's trusted artifact/job boundary without introducing a signing service.

**Acceptance.** The CI example accepts only matching successful evidence from its trusted producer and rejects stale/mismatched results or a forged self-consistent bundle. V09–V12 passing, with recorded evaluation results, closes milestone 3.

## Milestone 4 — Operator control and supervision

Entry gate: milestone 3. Control applies to every active agent invocation in `02`, `03`, `04`, `04_gate`, `05`, and `07`, including retries/fallbacks and agent-backed overseer calls. Omitted profile stages remain not applicable. Deterministic stages support controller holds and normal operator inputs, not model steering. This milestone extends V00 lifecycle, V09 capabilities, and V10 accounting; it does not relax cleanup guarantees.

### Slice V13 — Controllable agent sessions

**Problem description / scope.** One-shot subprocesses expose output but no supported route for mid-run input. Scope: session-capable adapters for existing providers and explicit intervention capabilities.

**Functional requirements**

- V13-FR1: Each adapter shall declare tested support for live steering, cooperative interruption, context-preserving continuation, and model/effort change boundaries. Expose supported, unsupported, or unknown through preflight and active-run status. The same capability checks shall cover every agent invocation listed above; unsupported steering shall offer an explicit alternative, never silently terminate or restart work.
- V13-FR2: Persist provider session/turn identifiers separately from controller run and stage-attempt identifiers. For persistent-session adapters, extend C03-FR1 with a confirmed successful terminal turn/attempt event, valid artifact, current inputs, and all execution guards as the promotion boundary; a live transport process or a message acknowledgment is not success. One-shot adapters still require successful process exit.
- V13-FR3: Isolate conversation state by task and stage/role; an independent reviewer shall not inherit the implementer's private session. Track owned subprocess/tool activity through interruption, reconnection, and shutdown. Close managed sessions when the controller run ends; unresolved ownership or delivery shall block unsafe continuation under C05/C08.
- V13-FR4: Keep a bidirectional control channel responsive while output is streamed. Enforce finite documented message-size, pending-request, and acknowledgment-timeout limits plus V00 output limits across continuations; overflow/disconnection shall expose rejected or uncertain delivery, not silently lose input or reset limits.

**Constraints.** Use documented interfaces for existing providers, without terminal keystroke emulation, a new provider, or an inference-engine implementation. Support may vary by adapter/version. Preserve the declared runtime through a compatible integration; do not silently raise the Python minimum. A retained session does not guarantee uninterrupted inference, zero additional tokens, or undoing tool effects.

**Acceptance.** Deterministic adapter fixtures cover all listed stages, normal/retry/fallback paths, terminal-event failures, disconnections, and session isolation. An explicitly authorized, budgeted smoke check demonstrates native steering on at least one existing provider; each other advertised capability has recorded version-specific evidence. Routine CI needs no paid calls.

### Slice V14 — Durable interventions and progression holds

**Problem description / scope.** A correction can arrive as an agent finishes or be mistaken for permission to change agreed requirements. Scope: new `control TASK --action steer|redirect|hold|resume|dismiss`, with `--message FILE` for steering/redirection and explicit target identifiers.

**Functional requirements**

- V14-FR1: Every control request shall carry a unique request ID, expected run ID, and control-state revision; agent-directed actions shall additionally bind stage and attempt IDs, resolved to the recorded provider turn. Persist requests before delivery through an owner-only local channel that does not wait on the target's execution lock. Serialize controller actions and reject stale, wrong-task, or wrong-attempt targets.
- V14-FR2: Record ordered request text/hash, target, time, and queued/delivered/rejected/uncertain disposition. Delivery shall require adapter evidence and shall not imply semantic compliance. Duplicate request IDs shall return the existing disposition; uncertain delivery after a crash shall be reconciled rather than blindly resent. Requests accepted before stage finalization shall be resolved or explicitly dismissed before promotion; late requests shall not spill into another stage.
- V14-FR3: `steer` shall deliver guidance without intentionally ending the attempt where supported. `redirect` shall confirm interruption before starting a recorded continuation/replacement; expose whether context survives and require explicit consent for a fresh invocation. Preserve partial files/output, original source baseline, consumed budgets, and C03-FR4's source-bound retry approval for interrupted writers.
- V14-FR4: `hold` shall durably prevent advancement into downstream stages, including deterministic final decision, without requiring the active agent to obey a message; it shall report whether current work is still running or quiescent. `resume` shall revalidate inputs, ownership, and authorizations without replenishing budgets. `dismiss` shall resolve only a named intervention and retain its history. Cancellation remains V07's managed stop, not a synonym for hold or steering.
- V14-FR5: Guidance shall not amend approved scope, requirements, permissions, or decisions implicitly. If the operator changes these, hold progression, quiesce affected execution, and use V04's explicit contract/artifact revision and invalidation route. Preserve stage responsibilities: revising a Stage 04 brief requires its gate to run again; steering its auditor shall not grant permission to rewrite the brief. Consumed interventions shall be bound into resulting attempt provenance and visible to required downstream review.

**Constraints.** Control responses acknowledge recorded actions, not successful task outcomes. Expose copyable target flags (`--run-id`, `--revision`, `--attempt-id`, `--request-id`) in status/watch; no internal-state editing is required. Guidance is not a guaranteed tool stop. No automatic rollback, gate bypass, cross-task broadcast, or automatic approval is introduced.

**Acceptance.** Interject during every active agent stage, including implementation and review. Completion races, duplicate submissions, lost acknowledgments, and controller restart cannot misroute a message or silently advance with unresolved accepted input. A hold accepted before the Stage 5 dispatch boundary prevents implementation even if the brief agent ignores guidance. Changed interrupted source requires bound approval before another writer starts.

### Slice V15 — Dynamic stage model and effort selection

**Problem description / scope.** Startup configuration does not give an operator a reliable way to adjust upcoming or active work. Scope: new `configure-stage TASK --stage STAGE --provider NAME --model NAME --effort VALUE --apply next|redirect` and read-only `--preview`; model/effort fields may be omitted when unsupported or unchanged.

**Functional requirements**

- V15-FR1: Preview and validate selections against V09/V13 capabilities, permissions, reviewer independence, and the current task. Precedence shall be explicit task-stage selection, project-stage setting, then provider default. Existing optional cost policy shall not override a pinned selection; an incompatible fallback shall block or use a separately approved provider-specific selection.
- V15-FR2: Persist configuration revisions atomically against the expected task revision; active-run changes shall also use V14's run/attempt targeting as applicable. Pre-run selection shall not require inventing a run or attempt. `next` shall affect the next dispatch or supported turn boundary, never claim to alter generation already in progress. `redirect` shall use V14 interruption/consent rules. Report the actual activation boundary and requested/effective settings; unsupported live changes shall not be silently ignored or restarted.
- V15-FR3: Bind effective settings and their revision to each attempt/continuation. Changes to completed stages shall affect only future authorized execution, not rewrite history or automatically repeat accepted work. Changed settings shall participate in the existing applicable input/evidence checks when that work is executed again.
- V15-FR4: Extend V10 accounting to explicitly started provider turns and replacement invocations, not merely operating-system processes. Reserve call allowance before each such start; a message appended to an existing turn is not itself a new failed attempt. Retain all observed usage and execution time across steering/redirects, including unknown observations. Time is excluded as human waiting only when no agent/tool work remains active.

**Constraints.** Operator control does not weaken budget, source-integrity, scope, or independent-review rules. Changing models/providers is not guaranteed to preserve a session. No automatic downgrade policy or promise that lower effort reduces total task cost is added.

**Acceptance.** Change selections for each applicable stage before dispatch and during a controlled run. Pinned selections survive optional cost routing; unsupported changes, races, and unsafe fallback fail clearly. Continuations cannot reset calls, time, or consumed approvals; previous attempts retain their original settings.

### Slice V16 — Multi-task operator supervision

**Problem description / scope.** Separate logs and status commands do not provide a usable view of several tasks needing intervention. Scope: new `watch [TASK]`, with a resolved-project task overview, task detail, `--json` snapshot, and explicit `--jsonl` event stream.

**Functional requirements**

- V16-FR1: Show each task's run/stage/attempt, last observed activity and freshness, effective/pending model settings, remaining budget with unknowns, hold/approval state, latest failure, and intervention dispositions. Provide filters for active, held, failed, and needs-attention tasks plus links to their current evidence.
- V16-FR2: Offer documented, fully targeted control/configuration commands from the displayed snapshot. Each mutating command shall revalidate its target and report its disposition and next action; read-only watching shall not acquire execution ownership, change state, or start providers. Human and JSON views shall use the same records.
- V16-FR3: Supervise independently running task worktrees without changing within-task stage order or allowing competing writers in one worktree. Show an intervention on one task separately from activity on another; detaching the watcher shall not stop either task or dismiss pending input.
- V16-FR4: Expose attention changes through terminal notices and JSON events with sequence/cursor information, so reconnecting consumers can identify gaps without inventing history. Provide a credential-free multi-task demonstration of steering, holding, changing a selection, and resuming without editing controller records. Unattended execution shall remain available unless a safety condition or explicit hold requires action.

**Constraints.** One local operator and one resolved project per view; no hosted dashboard, remote control service, multi-user authorization system, same-task parallel-stage scheduler, or autonomous task launching. Use bounded/paginated history and explicit stale/disconnected indicators; do not claim complete visibility into private model reasoning.

**Acceptance.** Supervise two isolated fixture tasks concurrently, correct one while the other continues, and reconnect without lost control dispositions or accidental retargeting. V13–V16 passing, including their capability evidence and requirement mapping, closes milestone 4.

## Milestone 5 — Run diagnostics and measured efficiency

Entry gate: milestone 4. Scope is understanding controller/provider failures and reducing repeated work, not automatically repairing the driven application or selecting cheaper models. Reuse V08 reports, V10 usage records, and V11 evaluation fixtures; preserve historical evidence and distinguish token usage, monetary estimates, elapsed time, and operator attention.

### Slice V17 — Run history and failure explanation

**Problem description / scope.** Latest-stage summaries hide the attempts, settings, and controller decisions that led to a fault. Scope: new `history TASK`, `inspect TASK --attempt ID`, and `compare TASK --attempts A B`, with human/JSON forms.

**Functional requirements**

- V17-FR1: Expose immutable per-attempt inputs/context, source and contract identities, effective settings, adapter/controller/schema versions, process/turn outcomes, interventions, validation results, and usage provenance. List attempts chronologically across retries/resumes; missing legacy data shall remain explicitly unavailable, not reconstructed as fact.
- V17-FR2: Explain why work dispatched, retried, fell back, was invalidated, promoted, held, or blocked using recorded controller rule IDs/versions and causal event references. Distinguish configuration/environment, provider/transport, artifact parsing/contract, controller/recovery, and driven-project verification failures; state unknown cause when evidence is insufficient.
- V17-FR3: Compare attempts' inputs, settings, artifacts, source identities, failure dispositions, and consumption. Separate observed differences from possible causes; do not infer that a model change fixed the problem merely because the next attempt passed.
- V17-FR4: Extend V08's report schema with ordered intervention/history references and supported next actions, with explicit schema compatibility. Diagnostic commands shall be read-only and provider-free; private raw prompt/output access shall be explicit and subject to existing runtime-data protections.

**Constraints.** Inspect observable inputs, events, outputs, and controller decisions; hidden reasoning is neither required nor asserted. No diagnostic claim may fabricate omitted records. Default summaries shall remain bounded; complete private evidence stays accessible by reference.

**Acceptance.** A fixture with provider failure, fallback, malformed artifact, intervention, and resume is explainable end to end. Comparisons identify changed settings/inputs without inventing causation, and damaged/legacy records produce useful partial diagnostics rather than acceptance.

### Slice V18 — Offline diagnostics and recovery previews

**Problem description / scope.** Debugging pipeline faults should not require paying for another generation or modifying the failed run. Scope: new `replay TASK --attempt ID --offline`, `diagnostics TASK --output PATH`, and `dry-run TASK --recovery`.

**Functional requirements**

- V18-FR1: Offline replay shall feed recorded inputs/events through parsing, artifact validation, and controller decision logic in isolated scratch storage, comparing derived outcomes with recorded ones. It shall start no provider, project command, hook, or verification process and shall never mutate the original task/source or authorize a live transition.
- V18-FR2: Record replay engine/version and supported capture versions. Missing required inputs or unsupported historical semantics shall produce incomplete/unsupported results; execution under newer rules shall be labeled a comparison, not exact reproduction of the old controller or model behavior.
- V18-FR3: Recovery preview shall list reusable/invalidated stages, outstanding interventions, ownership uncertainty, needed approvals, planned settings, and budget consequences without changing state. Return a recovery revision and a guarded `run TASK --expected-recovery REV` command; that command shall recompute the plan before execution and reject a changed plan. A preview is not retry approval or a spending authorization.
- V18-FR4: Diagnostic export shall create an atomic, versioned manifest of selected controller events, rule outcomes, versions, and record digests using an explicit metadata allowlist. Exclude credentials, environment values, raw prompts/transcripts/source, and host-absolute paths by default. Missing/redacted inputs shall be listed; full offline reproduction shall not be claimed for a reduced bundle.

**Constraints.** Reuse V08's no-overwrite/export safeguards and V00 privacy limits. Do not execute code embedded in captured data or download historical software automatically. Any live reproduction remains an explicitly authorized, budgeted normal run, separate from offline replay; no automatic repair of controller records is included.

**Acceptance.** Reproduce a captured parser/controller defect without provider credentials, project side effects, or original-record changes. Redacted/incomplete captures disclose their limitations. A changed recovery target cannot silently execute an outdated preview.

### Slice V19 — Safe evidence reuse and bounded context

**Problem description / scope.** Repeating valid stages and rereading unrelated history wastes work, while broad tasks lose important constraints. Scope: freshness-checked reuse and inspectable stage context, including `context TASK --stage STAGE`.

**Functional requirements**

- V19-FR1: Reuse completed task evidence only when recorded source, consumed artifacts/interventions, applicable configuration, contract, profile, and environment identities satisfy existing freshness rules. Record why each stage is reused or invalidated and repeat only affected work; unknown identity or superseding failed evidence shall prevent reuse. A completed result shall never be reused solely because its artifact exists.
- V19-FR2: Materialize a versioned, hashed stage context manifest containing required contract/criteria, relevant accepted decisions and corrections, current source/diff references, known risks, and unresolved findings. Identify affected systems and associated checks from recorded evidence, marking unknown impact explicitly. Operators shall be able to inspect the manifest before dispatch; it shall be retained with the attempt.
- V19-FR3: Enforce a finite configured context-input limit using the adapter's declared measurement method, reporting exact tokens, estimates, or byte limits honestly. Exclude redundant optional history first; mandatory constraints/evidence shall never be silently truncated. If required context cannot fit, block with an explicit action to narrow/split the task or amend the limit. This bounds controller-prepared input, not all subsequent provider tool reads.
- V19-FR4: Historical runs or other tasks may contribute explicitly selected, source-linked background context, but not automatic scope, instructions, acceptance, or verification credit. Generated summaries shall retain their source references and be labeled non-authoritative. Do not append complete transcripts by default or spend a model call to summarize them without explicit budgeted authorization.

**Constraints.** Preserve raw historical evidence; context selection is not deletion. No automatic task splitting, unverified repository-wide impact guarantee, hidden cross-task memory, or bypass of V04 scope amendments. New fingerprints do not prove behavioral correctness; required checks/review remain mandatory.

**Acceptance.** An unchanged resume avoids unnecessary dispatch; a changed dependency invalidates affected evidence while preserving valid upstream work. Mandatory constraints survive large-history context selection, oversized required input blocks clearly, and another task's passing report cannot authorize acceptance.

### Slice V20 — Repeated-failure prevention

**Problem description / scope.** Repeating an unchanged controller/environment fault consumes attempts without improving the task. Scope: explainable retry classification and suppression within existing retry/approval limits.

**Functional requirements**

- V20-FR1: Persist failure fingerprints from the failing component/rule and controller version, normalized error, relevant input/configuration/source/environment identities, and adapter version. Declare which classes are known deterministic faults, bounded transient failures, or unknown; similar prose alone shall not establish an identical deterministic cause.
- V20-FR2: Known deterministic preflight/controller faults shall block redispatch until a relevant input changes and revalidation passes. Repeated transient/unknown failures shall obey finite configured retry limits and existing approval rules; exhaustion shall expose history and the specific action required. Do not use another model call to repair a known controller parser/configuration fault automatically.
- V20-FR3: Any permitted operator-authorized retry shall record its reason, prior failure fingerprint, changed inputs if any, and approval consumption. Recheck writer/source and ownership guards; diagnostics, configuration changes, intervention, and resume shall not reset attempt or task budgets. An override cannot waive mandatory preflight or verification failures.
- V20-FR4: Aggregate recurring faults by component/stage/adapter with links to affected attempts and observed wasted work. Keep controller failures distinct from application-check failures and model-quality judgments; unknown attribution shall remain visible rather than being assigned to the selected model.

**Constraints.** Eliminate avoidable repetition, not promise error-free models, networks, or projects. No unbounded self-repair loop, automatic model downgrade, or new permission to overwrite source. Intentional project-code changes remain the normal task/follow-up workflow.

**Acceptance.** An unchanged missing prerequisite or controller parsing defect causes no further paid dispatch; a corrected input can pass revalidation. Transient retries remain bounded, and repeated manual actions cannot replenish the budget or conceal the fault history.

### Slice V21 — Efficiency attribution and evaluation

**Problem description / scope.** A lower-priced call, fewer tokens, and a cheaper accepted change are not equivalent. Scope: cost-of-rework reporting and evaluation of M4/M5 controls using the existing V11 benchmark.

**Functional requirements**

- V21-FR1: Report observed input/output/cache tokens, model/provider/effort, elapsed execution, intervention counts, and known operator-active time by task, stage, attempt, and continuation. Deduplicate cumulative provider observations; distinguish reported cost, estimates, unknowns, failed/superseded work, and reused evidence. Unrecorded operator attention shall remain unknown, not equal all held time. Attribute causes only where linked events support them; estimated avoided work shall never appear as observed savings.
- V21-FR2: Compare a fixed baseline with steering, explicit model/effort selection, valid-evidence reuse, and bounded-context variants on V11's versioned tasks, adding deterministic recovery/repeated-failure scenarios. Predeclare settings, budgets, criteria, and operator-intervention protocol; separate autonomous from assisted results and disclose combined changes that prevent isolating an effect.
- V21-FR3: Publish all attempts, including rejected, failed, cancelled, and incomplete work, alongside correctness, acceptance rate, operator time, and usage completeness. Report aggregate consumption and cost per accepted task with failures included; where no task is accepted or observations are missing, mark the metric undefined/incomplete. Do not recommend a default model/profile change from price or completion count alone.
- V21-FR4: Gate efficiency claims on recorded comparisons and retained safety regressions. Demonstrate that unchanged-evidence reuse and deterministic-failure suppression avoid additional dispatch in their fixtures; publish the live benchmark's measured benefits, regressions, and limitations without a guaranteed savings percentage. Any change to operator-pinned settings remains prohibited without explicit amendment.

**Constraints.** Live evaluation is opt-in and budgeted; routine CI uses recorded/fake providers. Provider caching is reported separately from reduced input and is not assumed free. Reuse existing reports/fixtures rather than adding an automatic optimizer, external analytics service, or billing guarantee.

**Acceptance.** An operator can explain a pipeline fault, preview safe recovery, inspect reused evidence/context, and account for intervention-related work without editing state. V17–V21 passing, with the comparative results and requirement-to-evidence record, closes milestone 5.

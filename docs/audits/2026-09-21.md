# Repository audit — 2026-09-21

Audited revision: `fad62ad`. Scope: documentation, runtime modules, tests, packaging, CLI workflows, and the product ideas in the existing untracked `docs/v2` and `CLAUDE-v3.md` files.

Catenna has a useful foundation: explicit stages, inspectable artifacts, bounded retries, provider adapters, verification execution, and substantial regression coverage. Its strongest product opportunity is a local tool that turns a bounded development task into an isolated patch with independent review and reproducible verification evidence.

The current acceptance and recovery guarantees need repair before expanding unattended use. Several reproduced paths report success despite failed or obsolete evidence. These are more consequential than adding providers, more planning stages, or a dashboard.

This audit changes no runtime implementation. Findings below distinguish reproduced defects from source-level risks and product recommendations. Existing untracked files were preserved.

## Priority fixes

P1 means a release blocker for the advertised acceptance, isolation, or recovery guarantees. P2 means a material reliability or usability improvement. No finding establishes remote exploitation or a malicious provider.

### A1 — P1: agent output can bypass verification, even when auto-verification is disabled

Evidence: [overseer.py](../../agent_pipeline/overseer.py), `ALLOWED_ROUTES` / `parse_overseer_candidate` at lines 9–21; [controller.py](../../agent_pipeline/controller.py), `run_overseer_or_fallback` at 1142 and the Stage 6 branch near 764.

The same parser accepts both external agent proposals and controller-generated handoffs. Its allowed routes include `auto_verified`. The controller upgrades eligible handoffs, but never rejects or removes an ineligible agent-provided `auto_verified` route. The Stage 6 branch subsequently trusts that route and writes an Accept checkbox.

Reproduced with a fake overseer returning `auto_verified`, a failed verification report, flagged coverage, `driven_project_verified=False`, and `enable_auto_verified=False`. The full real-driver fixture still returned exit 0 and Stage 8 `accept`.

Fix: separate the agent proposal schema from the persisted controller handoff schema. Only the controller may produce `auto_verified`. Recheck the evidence predicate at the Stage 6 transition itself. Add cases for absent/failed evidence, disabled auto-verification, and an agent claiming an unauthorized route. This directly contradicts the guarantee in `OVERVIEW.md` that the LLM cannot bypass the human checkpoint.

### A2 — P1: negative manual test outcomes become acceptance

Evidence: [artifacts.py](../../agent_pipeline/artifacts.py), `_manual_outcome_from_prose` and `_unit_has_accept_outcome`, especially line 488.

The prose parser matches positive words without accounting for negation. All three of these pass Stage 6 validation and classify as `accept`:

```text
Not approved.
Tests did not pass.
Do not accept this change.
```

A positive Stage 7 verdict then produces a deterministic false acceptance.

Fix: use an explicit typed decision or exactly one checked decision box as the authoritative value. Keep narrative evidence separate. If legacy prose must remain supported, accept only narrowly defined unambiguous forms and treat anything else as unresolved. Extending a free-text keyword classifier is a fragile basis for a release gate.

### A3 — P1: acceptance is not bound to the code that was tested

Evidence: [state.py](../../agent_pipeline/state.py), `reconcile_artifacts` at 156; [controller.py](../../agent_pipeline/controller.py), `run_real_pipeline` at 642; [verification.py](../../agent_pipeline/verification.py), report construction near 739.

Reconciliation hashes task documents. It does not compare the current source tree, base commit, verification commands, or effective configuration against the inputs used for verification and review.

Reproduced: complete an accepted task, create a new source file containing a runtime failure, then rerun the task. Both invocations returned exit 0; verification ran only once. The old acceptance remains current even though the working tree changed. A change while waiting for Stage 7 has the same missing evidence binding.

Fix: record a base commit, index/worktree patch identity, untracked-file hashes, and verification/configuration identity. Bind Stage 6, Stage 7, and Stage 8 to that snapshot. Source drift should invalidate verification/review, without automatically rerunning implementation. Reports should distinguish a historical acceptance from acceptance of the current patch.

### A4 — P1: read-only mutation detection is incomplete

Evidence: [controller.py](../../agent_pipeline/controller.py), normal guard at 901, completion path at 943, overseer dispatch at 1155, and `source_snapshot` at 1230.

There are three related problems:

- `source_snapshot()` compares porcelain status strings, not file contents. Editing an already modified file leaves the same ` M code.py` string. This is especially relevant to Stage 7, which normally reviews an already dirty working tree.
- The completion-only retry promotes its result without running the normal mutation comparison. A reproduced completion retry changed the snapshot and was accepted.
- The overseer takes the pre-call snapshot through `invoke_stage`, but its separate result path never compares it afterward. Verification has already run at this point.

Fix: centralize invocation and postconditions so normal attempts, completion retries, and overseer calls share them. Compare content/index fingerprints, and preserve evidence of any mutation. Read-only enforcement should also use the provider's supported execution controls; a post-run detector alone cannot prevent a write or detect every transient edit.

### A5 — P1: interruption leaves the child running after releasing the task lock

Evidence: [real_runner.py](../../agent_pipeline/real_runner.py), `run_to_files` at 209; [locking.py](../../agent_pipeline/locking.py), `TaskLock.__exit__`.

The child starts a new process session. Timeout handling kills its process group, but interruption has no equivalent cleanup.

Reproduced using a harmless sleeping child: send SIGINT to the controller, observe controller exit `-2`, task lock removed, and child still alive. A real implementation child could continue changing files or consuming resources while a new run starts. SIGTERM/controller death also needs an explicit orphan-recovery policy.

Fix: forward cancellation, terminate/reap the child group, and release ownership only after cleanup. Persist controller and child identities. Add a user-facing `cancel` command and tests covering SIGINT, SIGTERM, timeout, and abrupt parent death. Background launch should record an inspectable job identity and final exit status.

### A6 — P1: different tasks can concurrently modify the same working tree

Evidence: [locking.py](../../agent_pipeline/locking.py), per-task `TaskLock`; [controller.py](../../agent_pipeline/controller.py), `pipeline_run` / `pipeline_verify`; [verification.py](../../agent_pipeline/verification.py), `check_concurrency_guard` at 80.

Locks are scoped to task directories. Two task locks in one repository can both be acquired; verification checks only its own task lock. Both implementation runs can pass the initial clean-tree check before either edits a file. Verification, source inspection, and manifests can then observe another task's changes.

Fix: introduce repository/worktree ownership immediately. The stronger product design is one dedicated Git worktree per task, with verification and review running inside it. Keep per-task locks for task-state mutation as well. Test overlapping write/write and write/verify operations using separate processes.

### A7 — P1: crash recovery loses the provenance required to resume Stage 5

Evidence: [controller.py](../../agent_pipeline/controller.py), Stage 5 invocation at 694, first subsequent state persistence at 705, and artifact promotion near 909; [stage5.py](../../agent_pipeline/stage5.py), provenance lookup in `state.real_stage_runs`.

Attempt counts, assignments, the dirty baseline, and successful result metadata remain in memory through critical transitions. The runner writes sidecars, but recovery does not reconstruct the required state from them.

Reproduced an exception immediately after Stage 5 artifact promotion and before the next state write. No state file had been saved. The next run found the valid implementation report but blocked with `stage5_ambiguity`: no matching successful provenance record. The recent adoption fix only helps when the necessary provenance was already persisted.

Fix: persist a dispatch record and baseline before starting a write-capable process. Persist a completed run record and artifact hash through a recoverable promotion protocol. Reconcile interrupted transitions using durable sidecars/journal records. Inject crashes before and after each transition and prove that recovery neither repeats implementation blindly nor strands a completed change.

### A8 — P1: a valid-looking artifact overrides a failed subprocess

Evidence: [controller.py](../../agent_pipeline/controller.py), `ensure_real_stage` at 907–923 and the parallel completion branch.

The controller calls `atomic_finalize` and returns success before evaluating `result.failure_class`. A syntactically valid candidate from a timed-out or otherwise failed review can therefore become authoritative.

Reproduced a Stage 7 result with a timeout failure and a complete-looking review document. It was finalized and the stage returned 0. Stage 5 has additional provenance checks later; those do not protect every review stage.

Fix: require successful process/terminal-event status in addition to artifact validity. If selected failure classes support output salvage, make that an explicit, narrow policy with a distinct recovered state. An arbitrary failed review must not authorize acceptance.

## What the existing roadmap already has right

## Product recommendation

Assumed initial customer: an individual developer or small team working in existing Git repositories, using installed coding-agent CLIs, and wanting reviewable changes without continuous supervision. This is a product hypothesis to validate with users, not established market evidence.

Suggested promise:

> Turn a bounded development task into an isolated patch, independent review, and verification evidence you can inspect before merging.

The useful deliverable is a patch plus evidence and an explicit next action. Today the developer receives many documents, must manually seed strict templates, configure checks, interpret checkpoints, and manually turn rejection into follow-up work. Make that complete workflow the product.

The default success path currently calls an agent seven times: specification, specification audit, brief, brief audit, implementation, overseer, and diff review, before retries. Keep this thorough workflow available, but measure whether all seven calls improve outcomes for routine tasks. A simpler profile can preserve implementation verification and independent diff review while reducing planning handoffs. Introduce profiles only after the safety fixes and benchmark them against the existing pipeline.

### A tangible first release

The following commands describe a proposed interface; they do not exist today except for the current `init`, `run`, and `report` forms.

```bash
catenna init
catenna doctor
catenna task new fix-parser --request request.md
catenna run fix-parser
catenna report fix-parser --json
catenna export fix-parser --format patch
```

1. **Onboarding that completes.** Detect the repository, available CLIs and versions, and candidate project checks. Generate valid task templates with examples. Validate configuration and reviewer availability before any paid call. Include a local demo that needs no provider credentials.
2. **One isolated workspace per task.** Create a task worktree from a recorded base commit. Show exactly where the change lives. Preserve the developer's active work and make cancellation/recovery inspectable.
3. **An acceptance contract.** Give requirements IDs, expected behavior, constraints, and the check/manual evidence that proves each requirement. A passing unrelated command should not be presented as satisfying every requirement.
4. **A useful failure path.** Show what failed, the command/output that supports it, whether code was changed, and the next supported action. Add `cancel`, bounded retry, manual verification recording, and `followup` creation from rejected review items.
5. **A useful final result.** Present the patch summary, base commit, source fingerprint, checks, unresolved findings, effective agents/models, usage completeness, final decision, and the next command. Support a stable JSON output for editors and CI, plus Markdown for humans.
6. **Shareable evidence.** Export a patch and sanitized review/verification bundle. Add optional pull-request creation only after local export works well. Keep merge ownership explicit; the first useful release does not need automatic merging.

Use structured records for machine decisions and render Markdown from them. Codex already documents `--output-schema` for schema-constrained final output; other adapters should declare whether an equivalent capability is available. Local validation remains necessary even when providers support schemas. [Official non-interactive output documentation](https://learn.chatgpt.com/docs/non-interactive-mode).

### Architecture that supports that product

Preserve the existing modular work in `gates`, `stage5`, `decision`, `real_runner`, and `stream_events`. Refactor around concrete invariants instead of rewriting the orchestrator wholesale:

- A `RunContext` owns project root, task/worktree identity, effective configuration, provider versions, and storage paths.
- A shared stage executor owns dispatch, cancellation, process success, mutation checks, artifact validation, and durable completion. Retry paths should not duplicate these postconditions.
- A small decision policy consumes typed evidence. Agent prose cannot grant controller permissions or manufacture verification status.
- An evidence store gives each input, run, check, review, and patch a stable identity and atomic persistence. Existing file storage can remain; a database is not a prerequisite.
- Provider adapters declare model/effort/turn-budget/schema/cancellation capabilities and normalize events. Unknown event schemas should produce visible degraded observability.
- Verification adapters reuse the generic command runner. Start with configured commands and a few well-tested presets; avoid building a new test framework.

Protect the new boundaries with meaningful tests: process-level cancellation/concurrency, crash injection, source drift, malformed provider events, semantic decision inputs, and wheel installation outside the checkout. Add provider-version fixtures from sanitized real runs and a small opt-in live compatibility check. More tests mirroring the current implementation would not catch these classes of error.

## Recommended delivery order

| Milestone | Scope | Completion evidence |
| --- | --- | --- |
| 1. Trustworthy execution | A1–A8; explicit decisions; durable execution records; shared guards; source identity; cancellation; repository/worktree ownership; packaging CI | Every reproduced failure has a regression test with the corrected expectation; no accept without matching evidence; no orphan writer after supported cancellation; documented recovery after injected crashes |
| 2. Useful local product | `doctor`; task creation/templates; worktrees; project verification presets; manual-check recording; bounded follow-up; JSON report and patch export; rewritten quick start | A developer can install into a clean environment and complete a small Python or JavaScript task without editing internal state or inventing undocumented files |
| 3. Measured efficiency and team use | Capability-aware routing; task-wide call/time/token limits where enforceable; workflow profiles; outcome benchmarks; optional PR/CI integration | Published results compare the thorough pipeline and simpler profiles on the same tasks, showing reviewer effort, accepted-correct changes, escaped defects, time, usage completeness, and cost |

For task-wide budgets, distinguish hard controller limits (calls, elapsed time, retries) from provider-dependent token/cost limits. A displayed turn budget that the adapter cannot enforce is not a spending control. History-based model downgrading should account for semantic review outcomes and a bounded sample window; one old failure should not permanently dominate all future choices.

Suggested evaluation set: small bug fixes, changes spanning several files, refactors, missing-test tasks, intentionally failing builds, source drift, unavailable reviewers, and interrupted runs across a few example repositories. Use correctness and human review effort as primary outcomes. Stage completion alone measures whether the machinery ran, not whether it produced a good change.

Defer a hosted dashboard, a broad plugin marketplace, custom filesystem/search tools, and autonomous model optimization until the local workflow is reliable and measured. The repository already contains enough orchestration machinery to make a useful product; the next work should make its acceptance trustworthy and its output easy for another developer to use.
